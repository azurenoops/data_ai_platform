# Secret rotation runbook

> Operator runbook for rotating the platform's operator-managed Key Vault secrets. The platform's [`kv_secret_expiry`](../../infra/modules/alerts/main.tf) alert fires at T-30 days for every tracked secret; use this page to handle the rotation when an alert lands.
>
> See the [Ingestion hub](../INGESTION.md) for cross-cutting concepts.

## Tracked secrets

| Secret | KV name (default) | Source of truth | Cadence | Restart required |
| --- | --- | --- | --- | --- |
| AFS storage account key | `afs-storage-key` | Source AFS storage account | **90 days** | No (ADF reads at pipeline runtime) |
| SharePoint Lists app-reg client secret | `sharepoint-list-client-secret` | AAD app-reg | **90 days** (matches `az ad app credential reset --years 1`, rotated halfway) | No |
| SHIR host VM admin password | `shir-host-admin-password` | Generated by `random_password` resource | **365 days** | Yes (next-apply re-runs DSC) |

The exact secret names are configurable via the `*_secret_name` tfvars (e.g., `afs_storage_key_secret_name`) — the table shows defaults.

## When the alert fires

The `kv_secret_expiry-<name>` alert fires when the secret is within `kv_secret_expiry_threshold_days` (default 30) of expiry. Acknowledge by rotating per the relevant section below.

## Rotating the AFS storage key

```bash
# 1. Get a NEW key from the source storage account
NEW_KEY=$(az storage account keys list \
  --resource-group <source-rg> --account-name <source-sa> \
  --query '[1].value' -o tsv)   # use key2 to allow zero-downtime rotation

# 2. Update the platform KV secret
az keyvault secret set \
  --vault-name <platform-kv> \
  --name afs-storage-key \
  --value "$NEW_KEY" \
  --expires "$(date -u -v +90d '+%Y-%m-%dT%H:%M:%SZ')"

# 3. (No restart needed) — next pipeline run reads the new value
RG=$(terraform -chdir=infra output -raw RESOURCE_GROUP_NAME)
ADF=$(terraform -chdir=infra output -raw DATA_FACTORY_NAME)
az datafactory pipeline create-run \
  --resource-group $RG --factory-name $ADF \
  --pipeline-name pl_afs_to_adls

# 4. Verify the next run succeeded, THEN regenerate key1 on the source storage account
az storage account keys renew \
  --resource-group <source-rg> --account-name <source-sa> --key key1
```

The two-step rotation (read new from key2, then regenerate key1) keeps existing connections working through the rotation.

## Rotating the SharePoint Lists app-reg secret

```bash
# 1. Reset the app-reg credential (1-year expiry)
APP_ID=<sharepoint-app-reg-client-id>
NEW_SECRET=$(az ad app credential reset --id $APP_ID --years 1 --append \
  --query password -o tsv)

# 2. Update the platform KV secret
az keyvault secret set \
  --vault-name <platform-kv> \
  --name sharepoint-list-client-secret \
  --value "$NEW_SECRET" \
  --expires "$(date -u -v +90d '+%Y-%m-%dT%H:%M:%SZ')"

# 3. (No restart needed) — next pipeline run reads the new value
RG=$(terraform -chdir=infra output -raw RESOURCE_GROUP_NAME)
ADF=$(terraform -chdir=infra output -raw DATA_FACTORY_NAME)
az datafactory pipeline create-run \
  --resource-group $RG --factory-name $ADF \
  --pipeline-name pl_sharepoint_lists_to_adls

# 4. After a successful run, prune older credentials
az ad app credential list --id $APP_ID --query "[?endDate < '$(date -u +%Y-%m-%dT%H:%M:%SZ)']"
# Then `az ad app credential delete --id $APP_ID --key-id <id>` for each expired one
```

> `--append` keeps the previous secret valid until you delete it, enabling zero-downtime rotation.

## Rotating the SHIR host VM admin password

The admin password is generated by `random_password` in [`infra/modules/shirhost/main.tf`](../../infra/modules/shirhost/main.tf) and stored in KV by Terraform. To force a rotation:

```bash
# Taint the random_password to force regeneration on next apply
terraform -chdir=infra apply -replace='module.shirhost[0].random_password.admin'
```

The next apply:
1. Generates a new 32-char password
2. Updates the `shir-host-admin-password` KV secret (with a fresh 365-day expiry)
3. Updates the VM's admin password in-place
4. Re-runs the DSC extension (no SHIR re-registration; auth key unchanged)

> **Why a restart-equivalent?** The VM password change forces an OS-level credential rotation; existing RDP sessions are dropped. New RDP sessions need the new password — retrieve from KV:
>
> ```bash
> az keyvault secret show --vault-name <platform-kv> --name shir-host-admin-password --query value -o tsv
> ```

## Rotating the SHIR auth key (if compromised)

The SHIR auth key is generated and managed by ADF; it isn't an operator-managed KV secret. To rotate:

```bash
RG=$(terraform -chdir=infra output -raw RESOURCE_GROUP_NAME)
ADF=$(terraform -chdir=infra output -raw DATA_FACTORY_NAME)
SHIR=$(terraform -chdir=infra output -raw SHIR_NAME)

# Regenerate primary
az datafactory integration-runtime regenerate-auth-key \
  --resource-group $RG --factory-name $ADF \
  --name $SHIR --key-name authKey1

# Re-apply Terraform to push the new key into the host VM via DSC's protected_settings
terraform -chdir=infra apply
```

The `azurerm_virtual_machine_extension "dsc"` resource carries the auth key in `protected_settings` and re-runs when the upstream value changes; the DSC `Script` resource is idempotent and will re-register the SHIR with the new key.

## Verifying rotation

For all rotations, confirm the alert clears within 1 hour:

```kusto
AlertsManagementResources
| where properties.essentials.alertRule contains "kv-secret-expiry"
| project properties.essentials.alertRule, properties.essentials.monitorCondition, properties.essentials.lastModifiedDateTime
| top 10 by properties_essentials_lastModifiedDateTime desc
```

A cleared alert should show `monitorCondition == "Resolved"`.
